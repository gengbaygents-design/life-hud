ASSIGNMENT
==================================================

Assignment is one of the most important objects in LIFE HUD.

Hard invariant:

ASSIGNMENT != TASK

Assignment means:

“现实世界/课程要求我完成的东西。”

Task means:

“我要怎样执行它。”

Initial Assignment fields conceptually:

courseId

title

workState
submissionState

submittedAt nullable

version
createdAt

==================================================
WORK STATE
==================================================

Use a model equivalent to:

NOT_STARTED
IN_PROGRESS
DONE

Do NOT use SUBMITTED here.

==================================================
SUBMISSION STATE
==================================================

Separate from work state.

Use a model equivalent to:

NOT_SUBMITTED
SUBMITTED

Optionally later:
NOT_REQUIRED

but do not overbuild if unnecessary now.

Critical valid state:

workState = DONE
submissionState = NOT_SUBMITTED

This state MUST exist.

==================================================
CRITICAL INVARIANT
==================================================

DONE != SUBMITTED

Example:

User finishes 高数第三章作业.

The linked QUEST Task becomes:

COMPLETED

Assignment may become:

workState = DONE

But it MUST remain:

submissionState = NOT_SUBMITTED

until the user explicitly performs:

MARK SUBMITTED

or an equivalent explicit submission action.

Add automated tests proving this.

==================================================
ASSIGNMENT → TASK LINK
==================================================

When an Assignment is created,
LIFE HUD may create or propose a linked Core Task.

For this phase,
implement a deterministic integration rule.

Preferred initial behavior:

Creating a normal actionable Assignment
creates one linked Core Task
unless explicitly suppressed.

Example:

Assignment:
高数第三章作业

dueAt:
2026-10-XX 23:59

Linked Task:
完成高数第三章作业

sourceType = ASSIGNMENT
sourceId = assignmentId

Task dueAt should initially follow Assignment dueAt.

But:

Task remains Core.
Assignment remains University.

They are separate rows with separate IDs.

==================================================
DO NOT DUPLICATE SOURCE OF TRUTH
==================================================

Assignment is authoritative for:

course requirement
academic deadline
submission state

Task is authoritative for:

planned execution
start/complete/drop workflow
estimated work
QUEST scheduling

Do not store competing independent copies of academic meaning.

==================================================
ASSIGNMENT DUE DATE UPDATE
==================================================

Critical scenario:

Original:

Assignment dueAt:
Friday 23:59

Task plannedStart:
Thursday 19:00

Teacher changes Assignment:

dueAt → Monday 23:59

Expected:

Assignment dueAt changes.

Linked Task hard deadline should be updated to the new Assignment dueAt
because Assignment is authoritative for the academic deadline.

BUT:

Task plannedStart should NOT automatically change.

User's execution plan remains Thursday 19:00
unless user/system explicitly reschedules it.

This distinction is critical.

Add automated tests.

==================================================
TASK DELAY DOES NOT ALTER ASSIGNMENT
==================================================

Opposite direction:

Assignment dueAt:
Friday 23:59

Task planned:
Thursday 19:00

User delays Task:
Thursday 21:00

Expected:

Task plannedStart → Thursday 21:00

Assignment dueAt remains Friday 23:59.

No backward mutation.

==================================================
TASK COMPLETION REACTION
==================================================

When the linked Task completes:

Assignment workState may transition to DONE.

Assignment submissionState does NOT change.

Use a domain-event reaction/handler where appropriate.

Do not make QUEST secretly perform direct arbitrary writes into University tables.

Preferred architecture:

TaskCompleted event
→ University handler
→ linked Assignment workState update

Keep cross-domain direction explicit.
